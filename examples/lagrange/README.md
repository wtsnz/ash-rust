# lagrange

An interplanetary freight and docking platform built on **ash-rust**, and the deepest of
the examples: it uses nearly everything the framework does, on memory, SQLite and
Postgres alike.

Shipping lines (the tenants) book contracts, pack containers and fly voyages between
ports on planets and in orbit. The port authority runs the shared map of ports and
berths, customs inspects and seals dangerous goods, and ships report in through their
transponders.

```bash
cargo run -p lagrange -- simulate
```

## Domains

| Domain | Resources | Highlights |
| --- | --- | --- |
| `World` | `Planet`, `Port`, `Berth`, `BerthReservation` | Shared by every line. A generic `route` action prices a transit; berths are claimed under an optimistic lock; reservations are globally multitenant, with a composite foreign key that cascades a berth's recode and, on Postgres, a `btree_gist` exclusion constraint so no two holds on a berth overlap. |
| `Fleet` | `ShippingLine`, `CrewMember`, `Ship`, `Transponder` | Crew sign in with passwords (`#[authentication]`) and carry their role and line into policies. Ships are archived rather than deleted (`#[archival]`) and move through `docked → in_transit → maintenance` (`#[state_machine]`). Transponders authenticate with API keys. |
| `Cargo` | `Contract`, `Container`, `Voyage`, `Stowage` | Contracts and voyages are state machines; containers keep their manifest and customs seal behind field policies; voyages carry containers many-to-many through stowage slots, with aggregates for count, mass and hazmat. |
| `Telemetry` | `TelemetryPing`, `OpsEvent` | Kept in a separate SQLite database through a store tag. An audit notifier records every change, with the client's IP. |

The workflows that tie them together (reserving a berth, planning, stowing, clearing
customs, launching, arriving, completing, decommissioning) live in `src/ops.rs`, each in
one transaction.

## Features used

- **Resources**: identities (including partial ones), check constraints, hash, BRIN,
  partial and covering indexes, embedded resources (`Manifest`), `AshEnum`s, typed
  values (`CiString`, `Decimal`, `Date`, `UtcDateTime`, `Inet`, `Binary`, `Vector`),
  calculations with arguments, aggregates with filters, and Postgres-only statements.
- **Actions**: create, read, update and destroy actions with changes, validations,
  preparations and arguments; generic actions; upserts; bulk creates; keyset
  pagination.
- **Authorization**: policies with bypasses, actor attributes, `relates_to_actor`,
  `forbid_if` checks, and field policies.
- **Multitenancy**: attribute tenancy per shipping line, global resources, and reads
  that stay inside a line, including through relationships and aggregates.
- **Transactions and notifications**: `ctx.transaction`, which holds notifications until
  commit; PubSub, email (delivery notices), and a custom audit notifier.
- **Stores**: a `StoreRegistry` routing telemetry to its own database.
- **API**: GraphQL queries, mutations and live subscriptions, batched relationship
  loading, JWT sessions, and a generated TypeScript SDK with Zod schemas.
- **Migrations**: generated by `cargo-ash`, including a table and a column rename.

## Running it

```bash
# A week in the Sol system, in memory, or on SQLite or Postgres.
cargo run -p lagrange -- simulate
cargo run -p lagrange -- simulate --sqlite target/lagrange/fleet.db
cargo run -p lagrange -- simulate --postgres postgres://localhost/lagrange

# The API: GraphiQL at http://localhost:4000/graphql.
cargo run -p lagrange -- serve --port 4000
```

Sign in as any seeded crew member (each has the password `correct-horse-battery`) and
send the token as a bearer token:

```bash
curl -s localhost:4000/auth/sign-in -H 'content-type: application/json' \
  -d '{"email": "ada@helios-freight.example", "password": "correct-horse-battery"}'
```

```graphql
{ listShips { name captain { name } voyages { status } } }
```

Requests run as the token's crew member in their line: Ada sees Helios's ships, Mae sees
Red Dust's, and an anonymous request sees the public map.

## The SDK

```bash
cargo run -p lagrange -- sdk --out examples/lagrange/sdk/lagrange.ts
```

`sdk/lagrange.ts` is checked in; a test fails if it drifts from the resources.

## Migrations

`migrations/` holds the fleet database's history for SQLite and Postgres, written by
`cargo-ash` from the resources (the telemetry database is installed directly). From
`examples/lagrange`:

```bash
# Write the next migration after changing a resource.
cargo run -p lagrange --bin lagrange-codegen -- add_cargo_holds --dialect postgres

# Check the migrations are up to date.
cargo run -p lagrange --bin lagrange-codegen -- --check --dialect sqlite
```

## Tests

```bash
cargo test -p lagrange
```

Every scenario runs on memory, SQLite and, when `DATABASE_URL` is set, Postgres (with
the `citext`, `vector` and `btree_gist` extensions available):

```bash
DATABASE_URL=postgres://postgres:postgres@localhost:5432/ash_test cargo test -p lagrange
```

The SDK type check runs when `tsc` is installed.
